# 0007: Stage 1 starts with a batch mode; the core is separated through nine seams

- Status: accepted
- Date: 2026-11-10
- Needs owner approval: no (how to build it; the architect's call under record 0006). The owner approved the Stage 1 plan the same day.

## Context

- The owner asked for Stage 1 of `docs/roadmap.md` to be finished by the lead with its team.
- Two surveys of the code on 2026-11-10 mapped every tie between `core/` and the windows. Five files hold almost all of them: `core/undoaction.cpp` (243 references), `core/track.cpp` (33), `core/trackhandler.*` (28), `core/smoothhandler.*` (25), `core/sectionhandler.*` (21). The section maths, nodes, transitions and exporters are already free of the windows.
- Some model work lives inside the windows: loading a file creates sections by calling the track panel's "add section" slots; the roll-smoothing algorithm is in `ui/smoothui.cpp`; the project file's header is written by `ui/projectwidget.cpp`; the export file framing is in `ui/exportui.cpp`; eight undo cases do their work by calling widget slots. Recomputing a track rebuilds the 3D mesh in the same call, so nothing computes without OpenGL.
- No setting in `options.cfg` changes exported numbers. The core reads only `maxUndoChanges`.
- The baseline comparison took about a hundred mouse and keyboard actions per run. A refactor in eight pieces would need it eight times, by a lead with screen access, and the workers could not check their own pieces.

## Decision

1. **Batch mode first, refactor second.** The existing program gets a no-click mode (`--batch-export`) before the core is touched, and `tools/run-baseline.py` makes the comparison one command. Every worker then proves its own piece changed nothing. This pulls a slice of Stage 2's F2 forward; the proper command-line front end still comes in Stage 2, on the separated core.
2. **Test tracks are generated by a script inside the program** (`--batch-make-fixtures`), not clicked together. The 2016 binary is driven on screen only to open and export them. The same script checks undo: export, edit, undo everything, export again, compare; then redo.
3. **The core is separated through nine seams,** one or two per piece, each piece keeping the baseline passing:
   - S1 settings passed in (`maxUndoChanges`), no option reads in core;
   - S2 a change notice from the track ("geometry changed from node n", "status text"); the view rebuilds its mesh when told;
   - S3 the roll-smoothing algorithm in core;
   - S4 track display data (three colours, wireframe) as a plain struct in core, saved with the same bytes;
   - S5 loading builds sections through `track::newSection`; the anchor maths in core; the panel rebuilds its list from the model;
   - S6 tree rows owned by the UI, not by `sectionHandler`, `smoothHandler` or `trackHandler`;
   - S7 `trackHandler` split into a track document (core) and a track view (ui);
   - S8 undo resolves its target from stored indices and reports to a view interface; the eight operations that lived in widget slots become core functions;
   - S9 the project file and the export framing written by core.
4. **F1 ends with a proof:** a console program that links only `core/`, loads a project, computes and exports, and reproduces the baseline; and a check that fails if a file in `core/` includes a `ui/` or `renderer/` header or names `gloParent` or `glView`.
5. **The named command list is not part of F1.** F1 makes each edit a core function that the window and undo both call. The list of named commands with typed parameters and descriptions (FR-5, layer 2) is built on those functions in Stage 2, as piece T1 beside F2.
6. **Train data is one JSON file, `data/traintypes.json`,** read with Qt's own JSON classes and embedded through `resources.qrc`. No new dependency. Its loader gets the repository's first automated test, under `tests/`.
7. **The heartline picker fills the number only.** Which train was picked is not saved in the project until the `.fvd` format gains a field, with a version bump (rule 4 in `CLAUDE.md`).
8. **The owner's own projects are test tracks but not samples.** They are compared locally from `samples/private/` (ignored by git; `tools/run-baseline.py --extra`), because the fork is public. One goes into `samples/` only at the owner's word.

## Where enforced

- `docs/roadmap.md`, Stage 1.
- `docs/testing.md` once the batch mode is in.
- `.gitignore` (`samples/private/`).
