# Codebase map

What a session needs to find the right file in one read. It describes the code as it is at the end of Stage 1 (`docs/roadmap.md`). Each source folder has its own short guide: `core/CLAUDE.md`, `ui/CLAUDE.md`, `renderer/CLAUDE.md`. Terms: `docs/glossary.md`. Building: `docs/building.md`. Checking: `docs/testing.md`.

## What the program is

FVD++ builds roller-coaster track geometry from the forces the rider should feel (force vector design, after newton2). The designer chains **sections**; each section is integrated node by node at 1000 nodes per second of train time; the result is drawn in OpenGL, plotted, and exported to NoLimits 1 or 2 as a chain of Bézier segments.

## The three layers

- **`core/`** is the model: tracks, sections, nodes, the project file, the export files, the importers, smoothing, the train catalogue. It includes nothing from `ui/` or `renderer/`, names neither `gloParent` nor `glView`, and uses QtCore and `QColor` only. `tools/check-core.py` and the core-only program `fvdcore` (`cli/`, built into `build/dist/`; `tests/coreonly/` is the test that builds it from `core/` alone) enforce it.
- **`ui/`** is every window and the batch mode. It calls `core/` and `renderer/`.
- **`renderer/`** is the OpenGL view and the mesh builder. It reads `core/` and reaches into `ui/` through `gloParent` and `glView`.

The model tells the windows what happened through three interfaces it defines and the windows implement: `trackListener` (`core/tracklistener.h`), `smoothHandlerListener` (`core/smoothhandler.h`) and `projectFileClient` (`core/projectfile.h`).

## Build system and dependencies

- **`fvd.pro`** is the only build file for the program: qmake, `TEMPLATE = app`, `TARGET = FVD`, Qt modules `core gui widgets printsupport opengl`. It includes `core/core.pri`, the list of the model's source files, which the core-only program shares. There is no CMake file. The automated tests are small qmake projects of their own under `tests/`, built and run by `tools/run-tests.cmd` (`tests/README.md`).
- **Qt 5.** `fvd.pro` says "tested with 5.4.0"; `readme.txt` says v0.77 moved to Qt 5.2.1. The renderer is written against the Qt 4-era `QGLWidget`, `QGLShaderProgram`, `QGLBuffer` and `QGLFormat` from the `QtOpenGL` module (`renderer/glviewwidget.h`, `renderer/mytexture.cpp`, `main.cpp`). Those classes exist through Qt 5.15 and are gone in Qt 6, so a Qt 6 port means moving to `QOpenGLWidget` and friends.
- **Libraries outside the tree** (none vendored; on Windows they come from the MSYS2 packages or a machine-local `libs.pri`, see `docs/building.md`; `fvd.pro` defines `GLM_ENABLE_EXPERIMENTAL` and `GLM_FORCE_CTOR_INIT` so current glm behaves like the 0.9.5 the code was written for):
  - **GLEW 1.12.0** (Windows and Linux only; macOS uses the system GL3 headers). `bin/win64/glew32.dll` ships beside the binary.
  - **glm 0.9.5.1** (header-only maths; `lenassert.h` includes `glm/glm.hpp` and `glm/ext.hpp` with `GLM_FORCE_RADIANS`). Upstream issue altlenny/openFVD#5 reports that a current glm no longer compiles `core/track.cpp`.
  - **lib3ds 20080909** (the 2.0 API, `lib3ds.h`), used only by `ui/objectexporter.cpp` for the experimental `.3ds` export. `bin/osx64.zip` carries `lib3ds-2.0.dylib`. Optional on Windows: compiled in only with `qmake CONFIG+=with3ds` (`FVD_WITH_3DS`).
  - System OpenGL and GLU (`-lOpenGL32 -lGlU32` on Windows).
- **Vendored in the tree:** `ui/qcustomplot.cpp` and `.h`, QCustomPlot 1.2.1 (25,000 lines, half the repository). Never edit it; treat it as a library.
- **Resources:** `resources.qrc` embeds the shaders, `metal.png`, `background.png`, the six `sky/*.jpg` faces and the train catalogue `data/traintypes.json` into the binary; `common::getResource()` in `osx/common.cpp` (built on every platform) resolves files such as `options.cfg` next to the executable.
- **Platform code:** `osx/*.mm` and `osx/Init.cpp` (macOS document model, built only under `macx`); `winicon.rc` and `fvd.ico` on Windows. `main.cpp` installs a message handler that writes `fvd.log` in the working directory on Windows and Linux, and logs the OpenGL vendor, renderer and version at start-up.
- **Compiler assumptions:** C++03-era code with Qt containers, raw `new`/`delete`, `float` everywhere, `#define` constants, and raw `struct` writes to disk (see "Saved project file").

## Data model

Ownership runs project, then track, then section, then node. Everything is owned by raw pointer.

- **Project** = `projectWidget` (`ui/projectwidget.h`): `QList<trackHandler*> trackList`, the selected track `selTrack`, and the ground-texture path `texPath`. There is one project per main window (`MainWindow::project`).
- **`trackHandler`** (`ui/trackhandler.h`): one per track, on the window side. Creates and owns the model (`track* trackData`), its panel (`trackWidget*`), its plot (`graphWidget*`), its list row, its mesh (`trackMesh*`) and its undo history (`trackHistory* mHistory`). It implements `trackListener` and sets itself as `trackData->mListener`. The `track` knows nothing else about it.
- **`track`** (`core/track.h`): the anchor node (`mnode* anchorNode`, with `startPos`, `startYaw`, `startPitch`), the global physics inputs `fHeart` (heartline height in metres), `fFriction`, `fResistance`, the ordered `QList<section*> lSections`, the smoothing list `smoothList`, the draw style (`enum trackStyle`: generic, generic flat, Vekoma, B&M, triangle, box, small flat, double spine), the point-of-view position `povPos`, and `display` (`trackDisplay`: three `QColor`s and the wireframe flag, saved in the project). The whole track is one continuous chain: each section's first node is a copy of the previous section's last node, and `updateTrack()` re-integrates from a given section and node onward. The same node carries the force, so a force section starts from the force the previous section measured (`docs/research/r5-fvd-workflow.md`, A.1).
- **`section`** (`core/section.h`): abstract base with `QVector<mnode> lNodes` (one node per 1/`F_HZ` second; `lNodes.reserve(180000)` at construction), a `rollFunc`, and the parameters of every subtype in one flat set of fields. `enum secType` lists the kinds; `track::newSection()` is the factory (`core/track.cpp`):
  - `secstraight`: fixed heartline length `fHLength`, roll function over distance.
  - `seccurved`: `fAngle`, `fRadius`, `fDirection`, `fLeadIn`, `fLeadOut`; roll over the arc.
  - `secforced`: the FVD section. `normForce` and `latForce` are functions of time (`bArgument == TIME`) or distance (`DISTANCE`) giving the target vertical and lateral G; the integrator rotates the direction each millisecond so the rider feels exactly those forces (`updateSection()` / `updateDistanceSection()` in `core/secforced.cpp`). Speed is either carried from the previous node (`bSpeed`) or held constant at `fVel`.
  - `secgeometric`: same shape, but `normForce` and `latForce` are reused to hold **pitch change** and **yaw change** in degrees per second (`eFunctype funcPitch`/`funcYaw`), and forces are derived afterwards.
  - `secbezier`: a list of `bezier_t` control points (`core/mnode.h`), used by the NoLimits 1 importer and for hand-placed splines; no roll function.
  - `secnlcsv`: a track sampled from a NoLimits 2 CSV export (`loadTrack()` reads tab-separated position, front and left vectors); physics are simulated over the fixed geometry.
  - `bOrientation` chooses `EULER` (roll measured against the world up vector, so yaw adds banking) or `QUATERNION` (roll relative to the track).
- **`sectionHandler`** (`ui/sectionhandler.h`): one row of the track panel's section list. It does not own the section: the section belongs to the track. `trackWidget::sectionList` holds them.
- **`mnode`** (`core/mnode.h`): one sample of the train. Position `vPos` (this is the point the physics follows, **the heartline**; `vNorm` points from the rider toward the rails, so `vPosHeart(fHeart) = vPos + fHeart * vNorm` is, despite its name, the **track centre line**, which is what the mesh draws and the exporters write), the frame `vDir`/`vLat`/`vNorm`, `fRoll`, `fVel`, `fEnergy`, the felt forces `forceNormal`/`forceLateral` in G, the per-node deltas (`fPitchFromLast`, `fYawFromLast`, `fRollSpeed`, `fDistFromLast`, ...) and running lengths. `getPitch()` and `getDirection()` return degrees. `F_HZ` (1000) in this header is the integration rate used everywhere.
- **`func`** and **`subfunc`** (`core/function.h`, `core/subfunction.h`): a transition curve is a `func` (typed by `eFunctype`: roll, normal, lateral, pitch, yaw) made of consecutive `subfunc` pieces. Each piece has an argument range (`minArgument`..`maxArgument`, seconds or metres), a `startValue`, a change `symArg`, a shape `eDegree` (linear, quadratic, cubic, quartic, quintic, sinusoidal, plateau, tozero, freeform), a shape parameter `arg1`, and the time-warp knobs `centerArg` and `tensionArg`. `subfunc::getValue()` is the whole maths of transitions in one `switch`. A piece can be `locked` so it stretches to the section end.
- **Smoothing:** `smoothHandler` entries on the track (`core/smoothhandler.h`) describe a roll-speed moving-average filter, applied by `track::applyRollSmooth()` through `track::applyRollSmoothFilter()`. `updateTrack` re-applies it only once `track::bAutoSmooth` is set (the smoothing dialog was opened, or the project was loaded) and `track::smoothingActive()` is true. The smoothing dialog (`ui/smoothui.cpp`) owns the list rows and listens to each entry through `smoothHandlerListener`; the entry's name (`sName`) is what is saved.
- **Undo:** each track has a `trackHistory` (`core/trackhistory.h`, owned by its `trackHandler` as `mHistory`): the steps, each the track's whole state before and after (`core/trackstate.h`), a label, the commands that made it and the section and transition to select again. Every edit is a named command (`commandRegistry::run()`, `core/command.h`) that records its step; `trackHandler::undo()` and `redo()` put one back (`docs/decisions/0011-undo-by-snapshot-commands-on-top.md`). In the windows a run of values typed into one box is one step (`trackHandler::mergeWindowMs`).
- **Train catalogue:** `trainCatalogue` (`core/traintype.h`) loads `data/traintypes.json` into `trainType` entries. The Track Properties dialog (`ui/trackproperties.cpp`) offers them as "Train type" and fills the heartline box with the picked train's heartline (the number goes to `track::fHeart` like a typed one); which train was picked is not saved.
- **Constants** live in `lenassert.h` (`F_G` = 9.80665, `F_PI`, degree/radian factors, `TO_RAD`) and `core/mnode.h` (`F_HZ`). Friction and air resistance are per-track fields edited in `ui/trackproperties.cpp`; the energy update is in each section's `updateSection()` (for example `core/secforced.cpp`, the lines using `parent->fFriction` and `parent->fResistance`).
- **Maths that matches 2016:** `fvdmath::asinh2016()` (used by `subfunc::applyTension()`) and `fvdmath::asin2016()` (used by `section::calcDirFromLast()`) in `core/fvdmath.cpp` (`docs/decisions/0008-float-maths-reproduces-the-2016-runtime.md`).

### Saved project file (`.fvd`)

Binary, written field by field with the helpers in `core/exportfuncs.cpp` (`writeBytes`, `readInt`, `readFloat`, `readVec3`, ...). `writeBytes()` writes each block **back to front**, so numbers are big-endian in the file and a block of several values (a `vec3`, the three `QColor`s, the `"MELE"` tag of an export) appears in reverse order. The layout, and which function reads and writes which part:

| Part | Written by | Read by |
|---|---|---|
| 1. `"FVD"` then the version string `"v0.77"` (five bytes) | `writeProject()` (`core/projectfile.cpp`) | `readProject()`, which accepts `v0.77` and the legacy `v0.30` (routed to the `legacyLoad...` functions) |
| 2. The ground-texture path: `int` length, then the bytes | `writeProject()` | `readProject()`, then `projectFileClient::projectGroundTexture()` |
| 3. For each track, a `"TRC"` block: name (length-prefixed), the three `QColor` values **written as raw structs**, anchor position/roll/pitch/yaw/speed/normal/lateral, `fHeart`, `fFriction`, `fResistance`, draw flags, style, wireframe flag, POV position, the section count, then one section block per section, then the smoothing list, then `"EOT"` | `track::saveTrack()` | `track::loadTrack()` (old files: `track::legacyLoadTrack()`) |
| 4. A section block: a three-letter tag (`STR`, `CUR`, `FRC`, `GEO`, `BEZ`, `CSV`), the subtype's fields, then its functions; a function is `"FUNC"`, a count, and one `subfunc` record per piece | `saveSection()` in each `core/sec*.cpp`, `func::saveFunction()`, `subfunc::saveSubFunc()` | `loadSection()` in each `core/sec*.cpp` (the tag `switch` is in `track::loadTrack()`), `func::loadFunction()`, `subfunc::loadSubFunc()` |
| 5. The smoothing entries: count, then one record each | `smoothHandler::saveSmooth()` | `smoothHandler::loadSmooth()` |
| 6. `"EOP"` ends the project | `writeProject()` | `readProject()` |
| 7. The appendix, only when the project or a track has additions (`track::additions`, the client's `projectAdditions()`): `"FVX"`, the appendix version (`int`, 1, `APPENDIX_VERSION`), the length of the document (`int`), the document (compact UTF-8 JSON, written first byte first, `{"needs":[],"project":{...},"tracks":[{...},...]}`, one object per track in file order, each feature owning one key), `"EOX"`. Nothing after `EOP` otherwise, so a project without additions is written byte for byte as before | `writeAppendix()` in `writeProject()` | `readAppendix()` in `readProject()`; the 2016 program's reader stops at `EOP` (read from the code; to be tried on the binary) |

`saveProjectFile()` and `loadProjectFile()` open the file and call the two above. `projectWidget::saveProject()` and `loadProject()` call them with `this` as the `projectFileClient`.

**The appendix** (decision record 0014, points 14 and 15; root rule 4) is the one way to add a saved value that does not change the computed track. A track's additions are `track::additions` (a `QJsonObject`), part of its undo state (`trackState::additions`, compact JSON bytes); the project's own are kept by the client (`projectWidget::additions`, `coreProject::additions`) through `projectFileClient::projectAdditions()` and `projectAdditionsRead()`. Keys the program does not know are kept and written back. `readProject()` reads the appendix once every track is read, gives each track its additions and only then calls `projectTrackLoaded()` for the tracks, so a track's undo history starts with them. What a load does with an appendix:

| Found after `EOP` | The load |
|---|---|
| nothing | as before |
| a whole appendix, version 1, every check passed | the additions go to the project and the tracks; `"Load Successfull."` |
| an unknown name under `"needs"` (none is known yet) | refused: `"Error: This project needs ..."`; no track is kept |
| anything else: bytes that are not `FVX`, cut off in the tag, the version, the length, the document or `EOX`, a length that does not match, bytes after `EOX`, a version above 1 (a newer program) or below 1, a document that is not JSON or not an object, no `needs` list, an unknown key at the top, no `project` object or `tracks` list, a `tracks` count other than the project's, a track entry that is not an object | the tracks load as saved and every addition is dropped; the message starts `"Warning: "`, names the fault ("saved by a newer version of FVD++" for a version above 1) and says that saving will ask for a new file name; the client hears `projectFileClient::projectAdditionsDropped(reason)` |

**A dropped appendix protects its file.** The file still holds the additions, so nothing writes the project back over it: the windows forget the file name after such a load, as after File > New (`MainWindow::loadProject()` and `on_actionLoad_triggered()` read `projectWidget::additionsDropped`; the title shows "unsaved Work", Save asks for a name, the `.bak` autosave is off until then), and `fvdcore` refuses to write to the file it loaded, `--force` or not (`refuseOverwritingDropped()` in `cli/project.*`: `additions` without `--out`, `totext`, the session's `save` and `totext`, and the re-save of `export`, which never has that name anyway). Writing to another file is allowed and gives a project without the dropped additions. Batch mode loads through `projectWidget::loadProject()` and writes only into its output folder; the warning goes into its report.

**Errors and warnings are told apart by how the returned text starts** (`"Error"` or `"Warning"`), never by searching it: a warning can quote words from the file, such as the name of an unknown key.

The text form carries the same additions (`docs/project-text-format.md`). `fvdcore additions` shows and edits them (`cli/README.md`). `tests/appendix` checks all of the above.

Because structs and `QColor` are dumped raw (`track::saveTrack()` asserts `sizeof(QColor) == 16`), the format is tied to the compiler's layout and to the platform; each section class, function and sub-function also has save, load and legacy load on `std::iostream`. `MainWindow::backupSave()` writes `<name>.fvd.bak` every minute (`doAutoSave()`) and after each export.

Qt auto-connects slots named `on_<objectName>_<signal>()` to the widgets in the `.ui` forms, so renaming a widget in a form silently disconnects its slot and breaks the batch scenarios, which find widgets by those names.

## Where a change lands

## Known rough edges (not yet fixed)

What a build still warns about in the project's own files: deprecated Qt 5 calls (`QWheelEvent::delta()`, `qVariantFromValue()`, `QTreeWidgetItem::setBackgroundColor()`), which matter for a Qt 6 port (issue #3), and a few variables that are set and never read.

- Raw-struct file writes, including `QColor` and `bool`, make `.fvd` files compiler- and platform-specific.
- `core/secbezier.cpp.orig` is a leftover merge file that is not in `fvd.pro`.
- `ui/mainwindow.h` keeps a set of `#define` type codes (`STR_SEC`, `CUR_SEC`, ...) that duplicate `enum secType` with different numbering.
- Every GL call assumes GLEW initialised; `exit(4)` on failure.
- The Tangent exporter's handle length is `radius * tan(angle / 2)` (`mnode::exportNode()`), which blows up as a segment turns toward 180 degrees: in the baseline's tight loop it gives handles of about 8 m on a 2 m segment (`docs/testing.md`).
- The saved project keeps `"v0.77"` as its format version (`writeProject()` in `core/projectfile.cpp`); that is the file format's number, not the program's.
